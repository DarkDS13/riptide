02

The project in one page

If you only read one section, read this one.

The problem. Gzip is everywhere: logs, datasets, genomics archives, software packages. Decompressing a single .gz file is normally a one-core job, because each part of the file can refer back to data decoded just before it.

The base paper. Rapidgzip (Knespel and Brunst, HPDC 2023) already decompresses unmodified gzip files in parallel. Each thread decodes its own chunk without knowing the 32 KB of data that came before it, leaving placeholders called markers for the unknown bytes. Once the earlier data is known, the markers are filled in.

The gap. To fill in chunk k, you need the last 32 KB of chunk k−1 fully resolved, which needs chunk k−2, and so on. Rapidgzip resolves this chain of windows one chunk at a time. In section 2.2 the paper states that this propagation cannot be parallelised, and it attributes its scaling limit (around 64 cores on Silesia and 48 on FASTQ, without an index) to this step.

Our main contribution (M3) shows that this chain can be parallelised. It is a prefix computation, so a parallel scan resolves it in log₂N rounds instead of N−1 steps.

Two smaller contributions. M1 sizes chunks by estimated work instead of compressed bytes, and splits chunks that grow too large across idle threads; rapidgzip instead caps them, which serialises decoding above about 20× compression. M2 stores unresolved bytes compactly instead of widening every byte to 16 bits.

What we have shown so far. On the Silesia corpus, the same benchmark the base paper uses, our prototype resolves the windows exactly with the scan, and the final output is bit-identical to zlib. We have not yet measured any speedup; that is the implementation phase.

03

Five ideas you must understand

Every viva question about the method comes back to one of these.

1. Gzip refers back into its own output

Gzip (the DEFLATE format) compresses repeats by writing instructions like "copy 12 bytes from 5,000 bytes ago." These back-references reach at most 32 KB back. That 32 KB is called the window. To decode any position you need the window before it.

2. Reading is separate from copying

Turning compressed bits into symbols (a literal byte, or a copy instruction) needs nothing that was decoded earlier. Only executing a copy needs earlier output. So a thread can decode its chunk without the earlier data, and write a marker wherever it would have copied an unknown byte:

marker 256 + j   means   "byte j of the 32 KB window before this chunk"

This two-stage idea comes from pugz (2019) and is used by rapidgzip. It is inherited, not ours.

3. The window chain

After the first stage, the last 32 KB of chunk k is a mixture of known bytes and markers pointing into the window of chunk k−1. Call that mapping fk. Then each window is computed from the previous one: Wk = fk(Wk−1). Done in order, that is N−1 dependent steps for N chunks. This is the step the base paper says cannot be parallelised.

4. Why a parallel scan works (our main idea)

If you combine two of these maps, fk after fk−1, you get another map of exactly the same kind: every entry is still either a known byte or a pointer into an earlier window. And combining maps is associative: (a∘b)∘c gives the same result as a∘(b∘c). Any computation of the form "combine everything before me" with an associative operator is a prefix scan, one of the standard parallel algorithms. It finishes in ⌈log₂N⌉ rounds.

5. Work versus span

Work is the total number of operations; span is the longest chain of operations that must happen one after another. The scan does a little more total work than the chain, but its span is far shorter, and with many cores span is what limits speed. This is Amdahl's law: the serial part of a program sets an upper bound on speedup however many cores you add. In the real implementation we use a work-efficient scan (Blelloch's), which keeps total work proportional to the chain's.

04

What we have done so far

In order, including the two times we changed direction and why.

  1. August

    Problem statement (Component 1)

    Wrote and presented the one-page IEEE introduction: problem, background, gap, beneficiaries, novelty, evaluation and expected contributions.

  2. Early Oct

    Methodology drafts and a first pilot

    Built the methodology report and filled both course slide templates. Wrote a gzip decoder from scratch in Python that records every block, and checked it against zlib on four small files from our own machine.

  3. Early Oct

    First correction: load balance was overstated

    Our first framing led with work-sized chunking (M1). Modelling it honestly showed that rapidgzip's thread pool already hides most imbalance, so M1 could not be the headline.

  4. 7 Oct

    Base paper read in full; novelty re-anchored

    Read the whole rapidgzip paper and its changelog up to v0.16.0. Found that the paper itself calls window propagation unparallelisable and blames its scaling limit on it, and that nothing in the released software parallelises it. That became our primary contribution, M3. We also found that parallel CRC32 checking already exists, so we dropped it from our claims.

  5. 7 Oct

    M3 prototype

    Wrote a two-stage decoder that decodes chunks without their earlier data, then resolves the windows both one-by-one and by scan. Both gave identical windows, and the output matched zlib exactly.

  6. 7 Oct

    Moved everything onto Silesia

    Replaced the homemade test files with the Silesia corpus, the benchmark the base paper uses. Re-ran the profiler, the prototype at the base paper's 4 MiB chunks and at 512 KiB, and the M1 model. Updated the report and both decks.

  7. 7 Oct

    Second correction: the size of M3's effect is unproven

    The Silesia numbers showed the window chain is a small share of total work by pure arithmetic. M3 is still correct and new, but how much speedup it gives depends on what the step really costs inside rapidgzip. We removed a claim that our hardware would show the effect at 8–16 cores, and made timing that step the first implementation task.

Why the corrections are a strength

Both times we changed direction because our own measurements contradicted a claim, before anyone else caught it. Say this plainly if asked. Examiners trust a team that tests its own claims far more than a team with no visible weak points.

Slide 3

Methodology block diagram

On the slide
A two-row pipeline. Amber stages are ours; blue stages are inherited from the base paper. Below it, three cards compare each of our contributions with the base paper.
The stages
  1. 0Cost estimate. Read a few block headers to guess where the heavy work is. Cheap, and not a full pass over the file.
  2. 1Work-sized chunking (M1). Cut the file into chunks of similar estimated work, not similar compressed size. Oversized chunks are split and sent back to the thread pool (the dashed arrow).
  3. 2Speculative boundary search. Each thread looks for where a DEFLATE block starts inside its chunk. Inherited.
  4. 3Entry-point certification. Confirm the guessed start is real, because a wrong start silently produces garbage. Inherited.
  5. 4Parallel parse, span placeholders (M2). Every thread decodes its chunk at once, writing markers for unknown bytes. M2 stores those as compact runs instead of widening every byte.
  6. 5Log-depth window resolution (M3, primary). The prefix scan from section 03.
  7. 6Parallel materialisation. Replace markers with real bytes in every chunk at once. Inherited.
  8. 7CRC32 verification. Check the gzip file's own checksum. Inherited; the base paper's software already does this in parallel.
The three cards
  • M3 (primary): the base paper resolves windows one after another, calls that step unparallelisable, and attributes its 48–64-core limit to it. We use a prefix scan.
  • M1: the base paper cuts chunks by compressed size, balances by output size only when an index already exists, and its software serialises chunks above about 20× compression. We split those chunks across idle threads instead.
  • M2 (supporting): the base paper holds unresolved bytes at 16 bits until a chunk's window is free of markers. We keep output at 8 bits and record unresolved runs separately.
Say this

"Reading compressed bits doesn't need earlier output; only copying does. So every chunk decodes in parallel and leaves markers. Each chunk's final window is then a map from the previous window. Combining those maps is associative, so the chain the base paper resolves one step at a time is a prefix scan: log N rounds instead of N steps."

If asked
Which parts are yours? Only the amber ones; everything blue is inherited and credited.
Slide 4

Evaluation metrics and expected analysis

On the slide
  • A table with one metric per objective: correctness, resolution (M3), speed, cold start, overhead, load balance (M1) and memory (M2).
  • A box explaining why these metrics are enough, with baselines, repetitions, the statistical test and the ablation.
  • A chart of the M3 prototype on Silesia: 16 sequential steps become 5 scan rounds at 4 MiB chunks, and 130 become 8 at 512 KiB.
  • Three expected results.
What it means

Correctness is a gate: if the output differs from zlib by a single byte, no speed number counts.

Cold start times the first-ever read of a file, including our cost estimate, so M1 cannot hide its own overhead. Overhead compares our 1-thread time with igzip, the fastest sequential decoder, so our speedup isn't measured against a slow baseline we chose ourselves.

The chart shows depth, not time. It proves the scan reaches exactly the same result in far fewer dependent steps. It does not yet show a speedup.

Statistics: 10 runs per setting, medians, and the Wilcoxon signed-rank test, which compares paired timings without assuming they are normally distributed.

Say this

"Correctness first: byte-identical or it fails. Then one metric per contribution. The chart is our prototype on Silesia: the same windows, bit-identical output, in log N rounds. That's depth, not time. Before claiming a speedup we will time the serial step inside rapidgzip itself."

If asked
Isn't 16 → 5 just log₂? Yes: the counts follow from the algorithm. The real evidence is that the scan gives identical results on real data. What is the oracle λ? A simulation that assumes we know each block's true cost exactly, so it is an upper bound on M1's gain.

08

Honest limits and later work

Know these before an examiner raises them.

  • M3's speedup is unproven. The scan is correct and new, but by pure arithmetic the chain is small. Either the step costs much more inside rapidgzip than a 32 KB lookup (waiting for chunks in order, coordination on its main thread), or the paper's plateau has other causes too. Timing it is our first implementation task.
  • The step counts are arithmetic. N−1 against log₂N follows from the algorithm. What our prototype proves is that the scan is exact on real data.
  • M1's gain is modest on Silesia (λ 1.16 against 1.00 with 8 workers), and it's an oracle upper bound. If real measurements show compressed-size chunks already balance, we report M1 as a negative result.
  • Our decoder is a Python prototype, built to measure structure and check correctness, not for speed. The real implementation is a C++ fork of rapidgzip.
  • The dataset isn't finished. FASTQ reads, logs, high-ratio files and synthetic edge cases are planned.

Later work, in order

  1. 1Build rapidgzip from source and time its serial window step on Silesia at 4 MiB and 512 KiB chunks.
  2. 2Implement M3 (a work-efficient scan) in the fork, keeping output bit-identical.
  3. 3Implement M1's parallel splitting, then M2 if time allows.
  4. 4Run the benchmarks: thread counts, chunk sizes, cold and warm cache, 10 runs each, plus the ablation.
  5. 5Fill the final deck's amber cells and update its last two slides.
09

Questions to expect in the viva

Each of us should be able to answer every one of these.

What is your base paper, and what does it already do?

Rapidgzip, HPDC 2023. It decompresses ordinary gzip files in parallel: threads decode chunks without the earlier data, leave markers, and fill them in once that data is known. It reaches 5.6 GB/s on Silesia with 128 cores.

What exactly is new in your work?

Resolving the windows between chunks with a parallel prefix scan. The base paper says this step cannot be parallelised and resolves it one chunk at a time. We checked its changelog up to the latest version, and no release parallelises it.

Why does a scan work here?

Each chunk's final window is a map from the previous window: every entry is a known byte or a pointer into it. Combining two such maps gives another map of the same kind, and combining is associative. Any "combine everything before me" problem with an associative operator is a prefix scan, which takes log₂N rounds.

Doesn't the scan do more work than the simple chain?

A naive scan does. We use Blelloch's work-efficient scan, which keeps total work proportional to the chain's while cutting the span from N steps to about log₂N. With many cores, span is what limits speed.

Is that chain really the bottleneck?

The base paper says so. Our arithmetic says the chain is a small share of the work, so it may not be the whole story. That's exactly why our first implementation step is to time it inside rapidgzip, and why we haven't claimed a speedup yet.

How do you know your decoder is correct?

Every output is compared byte for byte with zlib, the reference implementation, and every gzip file's own CRC32 checksum is verified. All 13 Silesia streams match.

Why Silesia?

It's the standard compression benchmark and the one the base paper uses, so our numbers are comparable to theirs. Our tarball even reproduces the paper's 3.1 compression ratio.

What is λ, and why do you call it an oracle?

λ is the slowest worker's time divided by the average; 1.0 means perfectly balanced. The model assumes we know every block's true cost in advance, which a real system can't, so it is an upper bound on what M1 can achieve.

Rapidgzip already switches to 8-bit output. What does M2 add?

It does, once a chunk's window has no markers left. On Silesia with 512 KiB chunks, 78% of each chunk comes before that point, so the widened form dominates exactly when chunks are made small to save memory. M2 is labelled supporting for that reason.

What if M3 gives no measurable speedup?

Then we report it honestly, with the measurement showing where the time actually goes, and the result still explains the base paper's scaling limit. M1 and M2 remain as separate contributions.

Why not just switch to a better format like zstd?

Because the data already exists as gzip: logs, genomics archives, datasets. Converting it means decompressing it first, which is the slow step we're fixing.

What happened to the GPU idea?

The multicore CPU decoder comes first; a GPU version would be a feasibility study afterwards. Our contribution doesn't depend on it.

Glossary

Define each of these without hesitating.

DEFLATE
The compression method inside gzip, ZIP and PNG. Data is split into blocks.
Back-reference
An instruction to copy bytes from up to 32 KB earlier in the output.
Window
The last 32 KB of decoded output, which back-references can point into.
Marker
A placeholder for a byte whose value isn't known yet because it's in the previous chunk's window.
Two-stage decoding
Decode with markers first, fill them in later. From pugz; used by rapidgzip.
Chunk
The piece of the compressed file one thread decodes. Rapidgzip's default is 4 MiB.
Window chain
Each chunk's window depends on the previous one. Resolved one by one in the base paper.
Prefix scan
A parallel algorithm that computes every running combination of a sequence in log₂N rounds, if the combining operation is associative.
Associative
(a∘b)∘c = a∘(b∘c): the grouping doesn't change the result.
Work / span
Total operations / the longest chain that must run one after another.
Amdahl's law
The serial part of a program caps its speedup, however many cores you add.
ρ (rho)
Expansion ratio of a block: output bytes divided by input bytes.
λ (lambda)
Load imbalance: slowest worker's time divided by the average. 1.0 is perfect.
Oracle model
A simulation that assumes perfect knowledge, giving an upper bound.
Bit-identical
Our output equals zlib's byte for byte. Non-negotiable.
CRC32
The checksum stored in every gzip file, used to verify the whole output.
Silesia corpus
A standard 212 MB compression benchmark; the base paper's test data.
